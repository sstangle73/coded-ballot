Coded Ballot Design
Design discussion · 16 Nov 2026 · nothing built yet

One coded ballot, three ways to vote, one vote counted

An open source election system for member organisations run by volunteer tellers. Each member gets one ballot with a unique code. They can mail it, vote online with the code, or bring it to the meeting. The first use of the code counts and every later use is rejected. The secret ballot holds because no name ever appears on the ballot and no one keeps a list of who got which code. Each organisation's own rules live in a rules file, and counting methods are reviewed, pluggable modules. It is sized for clubs and nonprofits, not high-stakes public elections.

Every member gets one ballot with a secret code on it, but not their name. You can post it back, type the code into a website, or drop the ballot in the box at the meeting. Whichever you do first counts. If anyone tries the same code again, even with a photocopy, it's turned away. Nobody can tell which ballot is yours. It's made for clubs and charities, not for government elections.

How a vote travels

The issuer's tool runs on the issuer's own machine. It derives every code from a passphrase, sends the printable letters to a mail service or email service, and uploads only hash(S) and the ballot style. All three channels end at the same spend list, where one atomic update moves a code from issued to spent. Online choices are locked in the voter's browser with the tellers' count key, and stored with no code and no timestamp.

Think of the code as a cinema ticket with no name on it. The organisation prints one ticket per member and posts or emails it. The election website keeps a list of ticket fingerprints: it can tell a real ticket from a fake, but not whose it is. When a ticket is used, by post, online or in person, it gets torn. A torn ticket can't be used again. Your vote goes in a separate pile that has no ticket on it.

One code, used once

Each code is a credential, and the bearer is the voter. Its life is a small state machine on the server, keyed by hash(S). Spending it is a compare-and-set (UPDATE … SET state='spent', channel=?, at=? WHERE hash=? AND state='issued'), so two channels racing for the same code can't both win. First use wins. Re-voting or letting an in-person vote override an online one is impossible by design, because the earlier choice can't be found to remove it.

  • ✉ Mail: when an envelope arrives, tellers scan the QR code printed on the outside of the folded sheet, without unfolding it. That spends the code and starts the member's tracker. The folded sheet goes unread into a sealed box until the count.
  • ⌨ Online: code plus a one-time link sent to the member's own email (see the second-factor section below).
  • ▣ In person: the sheet is scanned as it goes into the box. If the member forgot their ballot, the issuer reissues it on the spot.
  • Copies (photocopies, home-printed PDFs, forwarded emails) carry the same S, so they need no special handling.

A ticket can be in only a few states: not used yet, used, or cancelled because the member lost it and got a new one. If someone photocopies a ticket, the copy has the same code. Whichever arrives second is turned away, and the tellers get a note about it.

Keeping the vote secret

Derived codes, no stored list. S = HMAC(K, election ‖ member_id ‖ n), where K comes from the issuer's passphrase. The tool runs locally (Docker or a signed release, never pages served by the public server, which could steal K). It writes letters and uploads hash(S) and the ballot style. To reissue, it recomputes S for member m, copy n, revokes its hash, and issues copy n+1. The public log shows only a count of reissues. This follows the same idea as Belenios's credential authority: the voting server sees credential fingerprints, never who holds them ✓.

Count key. The spend list and the choices are separate tables. Before voting opens, a teller creates a count key in the teller app. Their browser makes an X25519 key pair, uploads the public half, and shows the private half as a printable QR code or passphrase. The app won't open voting until a second copy is confirmed. The key's fingerprint is printed on every ballot sheet and in the election notice, so the operator can't quietly swap in a key of their own. Each online choice is encrypted in the voter's browser to the public half (a libsodium sealed box) and stored with no code and no timestamp, in shuffled batches, and the app doesn't log IP addresses. At the count the teller enters the key in the teller app, and their browser downloads the locked choices, unlocks them on that laptop, and counts them with the paper ballots. The server never holds an unlocked online vote. Paper choices are read from sheets that were spent earlier, at receipt.

Signed close. Closing voting is the issuer key's last act. A signing key derived from the same passphrase (a separate HKDF label from the code key) signs the close time and the SHA-256 of the full list of locked votes. The server publishes the statement, and then the passphrase is destroyed. The server refuses to hand over locked votes before a valid close, and every download attempt goes in the public log. The tellers' app checks the downloaded list against the signed fingerprint before it unlocks anything, so a vote added after close shows up as a mismatch.

Roles. Roles are configurable. In one-person mode the issuer and teller are the same person, and the close gate and log are guardrails, not a lock, because that person holds the count key throughout. In separated mode the issuer never holds the count key and can't unlock online votes at all. Optionally, the operator can be a third person.

Time-lock (opt-in). An election can also lock every online vote to the drand round that falls at the close time. The browser wraps the count-key sealed box in a time-lock layer (tlock-js, Apache-2.0 or MIT ✓, v0.9.0, last push March 2024 ✓). Until drand publishes that round, nobody can remove the outer layer, whatever keys they hold, so even one-person mode can't peek early. At the count, the tellers' app fetches the round from a public drand relay, removes the time-lock layer, and then unlocks with the count key. drand is run by the League of Entropy, whose members include Cloudflare.

Tamper checks. Every release is built reproducibly and publishes the SHA-256 of each file the voting page loads. While voting is open, the tellers' app fetches the live voting page from the teller's own device at intervals and compares it with the release, and logs every result in the teller report. Any member can run the same comparison from a check page hosted on the project's own public site, built from the repo and outside the organisation's control. It fetches the voting page from the member's browser and hashes it. A hash shown on the voting page itself proves nothing, because a tampered page can display the genuine one. Checks catch tampering aimed at everyone, and at anyone who checks. A determined operator could still serve a checker something different from a real visit (inference), so a page altered only for voters who never check can slip through.

Bring your own voting page. The voting page is also published as a static release, on the project's own site and as a download. The election link carries the server address and election ID after the #, which browsers never send to a server. A member using the project's copy signs in with the email link, locks the vote in their own browser, and sends only the locked vote to the organisation's server, which allows CORS from the project's site. Before it locks anything, that copy shows the count key's fingerprint and refuses to vote unless it matches the one printed on the ballot. The drand network's chain hash is a constant built into the release. Members who vote this way are protected even if the organisation's page is altered. The server still sees member and code together at the moment of voting, so this protects how someone voted, not whether.

Key destruction at close. Before the box is opened, the issuer destroys K, and the teller report records when. After that, the paper kept for the retention period (which still shows S) can't be linked to anyone.

Small groups. Separate ballot styles by membership class: a class that votes on fewer questions gets a shorter ballot. If a style or batch has fewer than about 5 ballots, the app warns and publishes only combined totals for the shared questions.

There's no list saying "Alice got ticket 7KQ2". Instead the issuer, the person who sends out the ballots, has a secret password, a bit like a recipe. Feed in the password and Alice's member number, and out comes her code. Without the password, nobody can work it out.

That recipe is how the issuer reprints a lost ballot. When voting closes, before the box is opened, the issuer destroys the password, and the tellers write down that it was done. From then on nobody can work out which ballot is whose.

If only two or three people use one kind of ballot, their votes could be guessed just from how few there are, so the app warns about that.

Online votes are locked as soon as they're cast, with a key a teller makes before voting starts. The website stores only locked votes, so even the person running it can't read them. At the count, the teller unlocks them on their own laptop and counts them with the paper ballots.

Closing the vote is the issuer's last job. Their password signs a note saying "voting closed at 8:02 pm, and here's the fingerprint of every locked vote", and then the password is destroyed. The tellers check that fingerprint before they unlock anything. A small organisation can have one person do every job, and a bigger one can split them up.

An organisation can also switch on a time-lock. Online votes are then also locked to the closing time, using a public service run by a group of organisations that includes Cloudflare. Nobody can open them early, not even someone doing every job.

The tellers' app also checks that the voting website is running exactly the published code, and writes down every check. Any member can run the same check from the project's own website. A fingerprint shown on the voting page itself doesn't count, because a faked page could show the right one.

Even better, a member can skip the organisation's page altogether and vote from the project's own copy. It checks that the lock it uses matches the fingerprint printed on their ballot, so their vote stays private even if the organisation's website has been tampered with.

Online needs a second key

This closes the issuer attack for online voting, where the issuer recomputes a non-voter's code. The member asks for a one-time link, which is sent to the email on the frozen roll. The link opens the voting page, where the member enters their code and choices. In one transaction the server marks the link used (one per member), spends the code, and stores the locked choice apart from both.

  • The roll, including emails, is frozen at the notice date. Every change is listed in the teller report and the old address is notified, so the issuer can't quietly change a member's email to one they control.
  • The server sees member and code together at the moment of voting. It doesn't store that link, but whoever runs it is trusted not to log it, as with most hosted voting services.
  • Members with no email on file vote ✉ or ▣.
  • If a member gets the ballot and the link by email, anyone who gets into that inbox has both.

The issuer can work out anyone's code, so online voting also needs something only the member has: a link sent to their email. Click the link, type the code, vote. Each link works once.

Scanning and counting paper

The ballot layout has four corner fiducials, a QR code (election, style, S, page) and large ovals. One TypeScript pipeline (OpenCV.js or WASM) serves both inputs: a phone-camera PWA, and a watched folder for flatbed or sheet-feeder scans run by the same core as a Node CLI. Steps: find the fiducials, correct the perspective, decode the QR code, then sample each oval's fill. Fills between two thresholds, overvotes and write-ins go to a teller adjudication queue with the image. Ranked ballots use a rank grid on the same pipeline. Each ballot yields a cast vote record (CVR) and a SHA-256 of its image. The app's tally is the working count. Tellers hand-count every paper ballot and enter their totals, and a mismatch blocks certification. Larger organisations can switch to a sampled audit; VotingWorks' Arlo (AGPL-3.0 ✓) is the reference.

Prior art: OMRChecker (MIT, active Sep 2026 ✓) for phone and scanner OMR. The VxSuite ballot interpreter is GPL-3.0-only ✓, so it can be read but its code can't be copied into an AGPL project (inference: interpreter code not read).

You can photograph a ballot with a phone, or put a stack through a scanner. The app finds the corner marks, reads the code, and checks which bubbles are filled in. Anything unclear goes to a teller to decide, with a picture of the ballot. Then the tellers count all the paper by hand. If their count and the app's count disagree, nothing is announced until they work out why.

Mailing ballots through an API

A mail company can print each member's letter and ballot, put them in an envelope with a return envelope, and post them. You send it a file; it does the rest. Nobody in the organisation ever folds, stuffs or even sees a ballot next to a name.

Two things don't change. The mail company sees names next to codes, because it prints them. And the issuer's password can still work out any code. So it takes volunteers' hands off the paper, but it doesn't remove the need to trust the issuer.

The catch is the return envelope. Neither mail company will put postage on it for a small organisation. Lob's return envelopes come without postage, and its prepaid option is only for its biggest customers. PostGrid sells return envelopes 5,000 at a time.

For an organisation of a few dozen members, the cheapest way to keep postal voting free for members is to print the packets, stamp each return envelope, and post them. That's about $90 for 50 members. Paying the Post Office only for the ballots that come back works out cheaper only for organisations with thousands of members.

What it takes.

  • An account with a test key and a live key, stored only on the issuer's machine and used by the local tool.
  • One API call per member: the address, a file (the tool's own 8.5×11 PDF, so the fiducials and ovals print exactly as designed), First-Class mail, and a return envelope. Lob's letters API takes return_envelope with a required perforated_page; PostGrid takes a returnEnvelope ID ordered in advance ✓. Both also accept HTML templates with merge variables ✓.
  • Test first: PostGrid says test-mode orders "will not be sent out" ✓.
  • Address verification is optional: Lob Developer charges $0.05 each ✓.
  • Mail class: PostGrid restricts Standard (marketing) class to marketing mail ✓, so ballots go First-Class, which PostGrid quotes at 5–7 business days ✓.

Effect on trust. It removes the stuffing step, where a volunteer sees code and name together, and adds a vendor that holds name, address and code. Neither Lob nor PostGrid states a retention period on the pages read ✓, so TRUST.md lists the vendor as a party that sees codes. A stricter no-key mode becomes possible: the tool generates random codes, sends them straight to the API, uploads hashes, and keeps nothing. Nobody in the organisation could ever recompute a code, but a lost ballot could then not be revoked. Ruled out: member elections need reissue.

Prepaid return.

  • Lob: its return envelopes "come without prepaid postage" ✓. Its Business Reply Mail is Enterprise-only, needs the customer's own USPS permit, and uses a USPS-approved design with no custom artwork ✓.
  • PostGrid: return envelopes are pre-ordered with a minimum of 5,000, and postage is not stated ✓.
  • USPS (DMM 505 and Notice 123 ✓):
    • a stamp on every return envelope: $0.82
    • metered prepaid reply: $0.78, which needs a meter or PC postage, an undated indicia and the "postage has been prepaid by" legend
    • Business Reply Mail (BRM) Basic: $390 a year plus $0.82 + $1.31 per returned piece
    • Qualified BRM: $1,130 a year plus $0.794 + $0.058 per returned piece, with USPS approval
  • Break-even: BRM Basic beats stamping every envelope only when N × (0.82 − 2.13p) > 390, where N is the number of members and p the share of ballots returned by mail. At 30% returns that's about 2,150 members; at 50% it never does. Qualified BRM at 50% returns needs about 2,870 members.

So the default mailing path for the niche is a print-at-home packet: per-member PDFs in mailing order, laid out for a #10 window envelope with the ballot folded code-inward, plus #9 return envelopes printed with the organisation's address and stamped by volunteers. The mail API stays as an adapter for larger organisations, where members supply their own stamp or an Enterprise contract adds BRM.

Weaknesses of the design

  • No coercion resistance: remote voting can't stop someone watching, or a code being sold. Helios's FAQ says online elections fit groups that don't expect large attempts at fraud or coercion ✓.
  • Small anonymity sets in a few-dozen electorate: the app warns but can't fix it.
  • Write-ins and handwriting can identify a voter to the tellers.
  • Key destruction can't be proven.
  • Not end-to-end verifiable: a member can check their ballot was received, not that it was counted as cast.
  • Online votes are locked with the tellers' count key, but whoever runs the server also serves the voting page and could change it to copy votes before they're locked. The tellers' checks, and members using the project-hosted checker, catch tampering aimed at everyone and at anyone who checks, but not a page altered only for voters who never check. Members who vote from the project's copy, and match the printed count key fingerprint, are protected either way.
  • Publishing the count key after certification lets anyone recount online votes, but a small ballot style or weight group can then be read in the published set too. The small-group warning covers this.
  • In one-person mode, the same person holds the count key all through voting. The close gate and the public log are guardrails, not a lock, unless the time-lock is on.
  • With the time-lock on, the count needs drand to be reachable, the close time is fixed when voting opens, and extending voting lets votes already cast be unlocked at the original time.
  • If every copy of the count key is lost, the online votes can't be opened.
  • An outage on the deadline day blocks online voting, and paper at the meeting is the fallback.
  • Some rules can't be offered: changing a vote after casting it, and enforcing limits on proxies.
  • Not certified, and not for public elections.
  • Someone could stand over a member while they vote at home, and the system can't stop that.
  • With very few voters of one kind, their choices are easier to guess.
  • A handwritten name in a write-in can give away who you are.
  • The issuer promises to destroy the password, and nobody can prove it was done.
  • You can check your ballot arrived, not that it was counted correctly.
  • The website can't read online votes, but whoever runs it must not secretly change it. The tellers' checks would catch most changes.
  • If one person does every job, the app stops them peeking early and logs any attempt, but it can't make peeking impossible unless the time-lock is on.
  • Lose every copy of the count key and the online votes are lost.
  • Once your vote is in, you can't change it.

Use something else when

  • The organisation can't name an issuer and an operator it trusts, and keep them as different people.
  • It expects coercion or vote buying.
  • It needs secrecy that holds even against its own officers. For online-only votes, Belenios (AGPL-3.0 ✓) or Helios (Apache-2.0 ✓) offer cryptographic guarantees.
  • The organisation doesn't trust its issuer and its website operator to stay honest and separate.
  • People might be pressured into voting a certain way.
  • The vote must stay secret even from the organisation's own officers.

Each organisation's own rules

The rules system has three layers.

  • Settings. A YAML rules file checked against a published schema. It holds anything that is a value: deadlines, which channels are allowed, who is eligible for which question, seats, write-ins, quorum, tie-break order, retention, and notice wording. The schema grows by release.
  • Modules. Anything that is behaviour is a small module in the project's code, added through review with its own tests. Interfaces:
    • count(records, contest) → result + explanation
    • eligible(member, contest) → weight
    • layout(contest) → ballot regions
    Organisations don't write scripts. That keeps every election's logic code that has been reviewed and can be audited.
  • Audit binding. The teller report records the rules file's SHA-256 and the software version. Every count module writes a step-by-step explanation a member can follow, such as each round of a ranked count and each transfer in STV.

Counting modules in the first version:

  • plurality, single and multi-seat
  • yes/no with any threshold, of votes cast or of members
  • approval
  • ranked choice, both IRV and STV
  • weighted votes, for example one vote per unit or per share

Ranked ballots use a rank grid (candidates × ranks) through the same scanning pipeline. Skipped or repeated ranks go to the tellers.

Every organisation runs its votes differently. Some need two-thirds to pass a motion, some let you rank candidates, some give each house or share one vote. The organisation writes its own rules into a settings file. How votes are counted comes from tried and tested building blocks that anyone can inspect. The final report says exactly which rules were used, and shows the count step by step.

What already exists

The only product that states it stops double votes across mail, online and in-person voting is commercial (Simply Voting: "voter strike-off" plus "unique, anonymous QR code" ✓). The open source tools are online-only or built for government elections. That gap is this project's niche: elections run by each organisation's own rules, for clubs, nonprofits, HOAs and union locals, with tellers, on cheap hosting.

Paid services already do this. Free, open tools either do online voting only or are built for government elections. Nothing open does what a small member organisation needs.

What gets built first

First version

  • Roll import (CSV) with membership classes, frozen at the notice date

  • Local issuer tool: derived codes, PDFs, mail API and email, reissue, key destruction
  • Online voting: a one-time email link plus the code
  • Count key: online votes locked in the browser and unlocked on a teller's laptop at the count, with two copies required
  • Configurable roles (one person or separated); the issuer key signs the close; counting checks that signature
  • Release hashes, tamper checks of the live voting page from the tellers' app, and a member checker hosted on the project's own site
  • Optional drand time-lock: online votes also locked to the close time
  • Project-hosted and downloadable voting page, checked against the count key fingerprint printed on the ballot
  • Practical safeguards: QR on the outside of the fold, provisional ballots, count key published after certification, passphrase backup and fallback close, drand-drawn lots, WCAG 2.1 AA and large print, clone as runoff, and a legal note in the README
  • Teller PWA: arrival scan, count scan, adjudication, hand-count entry
  • Public page: tracker, counts by channel, certified results, teller report
  • Purge when retention ends, with a log of what was destroyed
  • Load the member list
  • Set the rules from the organisation's rulebook, including ranked and weighted voting

  • Large-print ballots and a page that works with screen readers

  • One web framework for both (Hono runs on Workers and Node: inference). D1 is SQLite underneath, so one schema covers both
  • CI tests both targets
  • Voter-facing parts run on reliable hosting, not a home connection
  • Licence AGPL-3.0
  • Runs free on Cloudflare, or on any computer with Docker
  • Open source, and anyone who changes it and offers it as a service has to share their changes

Decisions so far

  1. The code goes on the ballot sheet itself. No envelopes and no name on the ballot. Copies are harmless because the first use wins.
  2. Codes are derived from the issuer's passphrase. No list is ever stored. The passphrase is destroyed and logged at close.
  3. First use wins. Mail is spent on arrival, and the marks are read at the count.
  4. Online votes are locked in the voter's browser with a count key a teller creates before voting (two copies required), and unlocked only on a teller's laptop at the count. They're stored without codes or timestamps, in shuffled batches.
  5. A public tracker, with results after the tellers certify them.
  6. Cloudflare and Docker both in the MVP, sharing one core.
  7. Licence: AGPL-3.0.
  8. Scanning by phone camera plus a watched scanner folder.
  9. The app counts and the tellers verify with a hand count. A mismatch blocks certification.
  10. Separate ballot styles by class, with a small-group warning.
  11. TRUST.md in the repo, linked from the README.
  12. Online votes need a second factor: a one-time link sent to the member's own email.
  13. Mailing for small organisations: print-at-home packets with a stamped return envelope (about $90 for 50). The mail API is an adapter for larger organisations.
  14. Reissue is required, so the issuer passphrase stays and no-key mode is ruled out.
  15. Rules are open-ended: values go in a schema-checked rules file, and behaviour comes from reviewed code modules. Organisations don't write scripts. Each teller report records the rules hash and the software version.
  16. The first version counts by plurality, yes/no with any threshold, approval, ranked choice (IRV and STV), and weighted votes.
  17. Kept proportionate: no ElectionGuard, no key-splitting ceremony, no blind signatures. This is for clubs and nonprofits, not high-stakes public elections.
  18. A count key, made by a teller before voting, locks online votes. The server never holds an unlocked one.
  19. Tamper checks: each release publishes file hashes, and the tellers' app checks the live voting page against them during voting and logs the results.
  20. Roles are configurable: one person, or separated. The issuer key signs the close, and counting needs the count key and checks that signature.
  21. A drand time-lock is an opt-in in the first version: online votes are locked to the close time as well as the count key.
  22. Members can vote from the project's own copy of the voting page. The count key fingerprint is printed on every ballot, and the project's copy won't vote unless it matches.
  23. Practical safeguards: QR on the outside of the folded sheet with plain return envelopes; provisional ballots for disputed members; the count key published after certification for public recount; a second copy of the issuer passphrase and a tellers' fallback close; ties drawn from drand; WCAG 2.1 AA, large print and online as an alternative; clone as runoff; and a README note that each organisation checks its own rules and law.
